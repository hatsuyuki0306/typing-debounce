# 打字感知防抖 —— 让聊天机器人在你打字时不抢话

> 给 OneBot / NapCat 生态的一个通用改造：**检测到对方还在打字就不要回复**，
> 等真正停手后再一次性回应。
>
> 这个仓库不讲「怎么做个 AI 女友」，只讲一个具体工程问题的完整解法：
> **如何在第三方插件的官方调度器里，无侵入地加一层「打字状态感知」。**

---

## 问题

聊天机器人有一个很破坏体验的行为：**你话还没说完，它已经回了。**

常见做法是「消息防抖」——收到消息后等 N 毫秒，没新消息再回。但纯静默计时有两个对称的缺陷：

| 窗口设小 | 窗口设大 |
| --- | --- |
| 你一句话还没打完，下一个字还没发，计时先到期 → **抢话** | 你确实说完了，还得白等那么久 → **迟钝** |

真正的解法不在「时间长短」，而在于要知道**对方此刻是不是还在打字**。

QQ（通过 NapCat）确实会推送这个信息 —— 一个 `input_status` notice。
但**直接用它做判断会踩三个坑**，每一个都能让功能表面正常、实际失效。

---

## 三个真实踩过的坑

这三个都是实测出来的，不是推演。改代码前请务必读完。

### 坑①：NapCat 的「正在输入」是每 5 秒推一次

实测时间戳（`12:05:03 → 08 → 13 → 15 → 20 → 35`），**间隔 5 秒**。

推论：**任何小于 5000ms 的静默窗口都不可靠。**

我第一版把窗口设成 3500ms，结果线上实测：

```
inbound   ts=...536023   消息到达
dispatch  ts=...539542   派发给模型      ← 间隔 3519ms
```

3519ms < 5000ms。你还在打字，但**下一个「正在输入」信号还没到**，她就开口了。

**这不是调参能解决的，是硬限制。** 窗口必须 > 推送间隔，我最后定 `6500ms`（5 秒 + 1.5 秒余量）。

### 坑②：按下发送键会先推「停止输入」，消息之后才到

QQ 的行为是：你按发送 → 输入框清空 → 立刻推「停止输入」→ **然后**消息才被服务器分发下来。

实测序列：

```
12:05:13  停止输入     ← 按了发送键
12:05:13  接收消息     ← 同一秒，但在停止信号之后
```

**所以「停止输入」这个信号本身绝不能触发回复** —— 它总是在消息之前到达。

如果拿它当「他说完了」的判据，你会在他按下发送的瞬间就派发，等于完全没有防抖。

正确做法：它只用来**更新打字状态**（表示"他停手了"），派发时机仍由「消息到达 + 安静窗口到期」驱动。

### 坑③：新消息到达、以及派发完成之后，都不能清掉打字历史

这条最隐蔽。

自然的想法是「收到新消息 = 他显然不在打字 → 清掉打字态」。**错的。**
他完全可能发完一句就接着打下一句。

更隐蔽的是第二处：**派发完成之后也不能清**。

因为一旦清掉，系统就认为「这个会话从没出现过打字信号」，下一轮会退回短窗口（3500ms）。
而如果他正在连续打字，下一个「正在输入」最多还要 5 秒才到 ——
**3500 < 5000，又变成抢话。这就是坑①的翻版。**

正确做法：保留「这个客户端会推送打字状态」这个**事实**（`firstSignalAt`），
只把计时锚点挪到当前时刻。

---

## 解法

核心判据只有**一条公式**，锚点是「最后一次打字信号」而不是「消息到达」：

```
有打字历史：
    wait = quietMs - (now - lastSignalAt)        # quietMs 默认 6500
从没出现过打字信号：
    wait = 3500 - (now - lastActivityAt)
打字感知关闭：
    wait = min(600, 3000 - (now - firstAt))      # 上游原有行为
```

返回 0 就派发，否则重排计时器。

### 为什么一条公式就够

不需要再叠一层「信号过期」判断：

- **他还在打字** → NapCat 每 5 秒推一次，每次信号都把 `wait` 重新拉回 ~6500ms
  → **永远不会派发**
- **他停手了** → `lastSignalAt` 定格 → 6500ms 后自然派发一次
- **坑②保证**「停止输入」先于消息到达 → 锚点正好是他按下发送的那一刻，
  比从消息到达起算更准

### 一个容易忽略的细节：过期刷新

如果上一条打字信号已经超过 `TYPING_STALE_MS`（8000ms），说明那批信号早断了。
这时新消息到达要把锚点挪到消息上，否则 `quietMs - (now - 陈旧锚点)` 会算成负数
→ 立刻派发 → 又是抢话。

### 设计要点

**1. 无侵入合并，不另写一套**

原插件（`dsh-onebot-qq` 0.10.0）已经有官方 `InboundScheduler`，解决了两个问题：
每会话串行链（带图慢消息不插队）、连发合并（几条短消息并成一条投递）。

我的做法是**加进它，而不是绕过它**：
新增 `noteTyping(key, isTyping)` 入口 + `typingStates` 状态表 + `nextWait()` 判据。
打字感知关闭时（`typingAware: false`），整个模块行为与上游**逐字节等价**。

**2. 两条 notice 通道分开**

官方 `onNotice` 只放行 poke（戳一戳）。所以要另开一条：

```
connection.onTypingNotice   ← 新通道
notice 门里按 sub_type === 'input_status' 分流
```

好处：poke 的节流/过滤逻辑不会顺手把打字信号吞掉，两者互不影响。

**3. 五个触点，少一处就静默失效**

| 文件 | 改动 |
| --- | --- |
| `connection.js` | 新增 `onTypingNotice` 字段；notice 门加 `input_status` 分支 |
| `index.js` | 接线 + 三个配置项（`typingAwareDebounce` / `inboundQuietMs` / `inboundTypingMaxMs`） |
| `bridge.js` | `onTypingNotice()` 入口，转交调度器 |
| `inbound-queue.js` | 核心逻辑 |
| 配置文件 | `inboxQueueEnabled: true` ← **前置条件，关掉就全废** |

**这类功能最危险的失败模式是「不报错地失效」** —— 代码在、配置错，功能就是没有。
所以这个仓库还配了**反向断言**（见下文）。

| 组 | 验证什么 |

| 基线 | 无打字能力时用短窗口，不白等 |
| 坑① | 连续 6 次打字信号，全程不派发；停止后满窗口才派发 |

| 坑② | 停止信号先到、消息后到，仍按窗口派发 |
| 坑③ | 第一轮派发后，第二轮打字 4 秒仍不派发（若丢历史会在此抢话） |

| 命令直通 | 斜杠命令不参与防抖 |
| 多会话 | A 在打字不影响 B |

**测试原则**：`import` 真实模块，用假时钟接管 `setTimeout`/`Date.now`，
**绝不把逻辑抄一遍**。抄一遍的测试什么都测不到。

## 三条反向断言（比正向更重要）

正向断言只能证明「代码在」。而这类功能失效时**代码往往还在**，只是行为变了。
所以还需要「禁止出现某段代码」的检查：

| 断言 | 守护什么 |
| --- | --- |
| 禁止 `notice / request events are intentionally ignored` | 一旦出现说明被回滚成「notice 一律丢弃」，打字感知静默失效 |
| `flush()` 里禁止 `typingStates.delete` | 出现就在坑③上翻车 |
| `INBOUND_TYPING_QUIET_MS` 必须 > 5000 | 防抖是否真的有效 |

## 适用范围

- **OneBot v11 协议**的机器人（NapCat / go-cqhttp / Lagrange 等）
- 该协议通过 `notice_type: notify` + `sub_type: input_status` 推送打字状态
- **只适用于私聊**：群聊里「谁在打字」无法可靠归属

### NapCat 事件真实结构

```js
{
  post_type:   "notice",
  notice_type: "notify",
  sub_type:    "input_status",
  user_id:     <对方QQ>,
  event_type:  1,                     // 1 = 正在输入
  status_text: "对方正在输入..."       // 空串 = 停止输入
}
```

代码里**同时**用 `status_text` 和 `event_type` 判断，任一缺失都能工作
（不同 NapCat 版本可能只填其中一个）。

## 配置

```yaml
inboxQueueEnabled: true       # 前置条件：不开启调度器，打字感知无处落地
typingAwareDebounce: true     # 总开关
inboundQuietMs: 6500          # 必须 > 5000（见坑①）
inboundTypingMaxMs: 45000     # 绝对上限，防止永远不回
```

### 调参指南

| 症状 | 怎么调 |
| --- | --- |
| 他还是打字时就被回了 | `inboundQuietMs` **调大**到 8000–10000 |
| 他说完后等太久 | 先确认不是坑③（看日志里「打字历史=True」才对） |
| 完全没反应 | 查 `inboxQueueEnabled` 是否为 true；查 `input_status` 有没有进到 bridge |
