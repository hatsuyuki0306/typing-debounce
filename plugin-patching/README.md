# 升级第三方插件，但不丢自己的定制

> 一个通用工程问题：你深度修改过一个 npm 包，下次 `pnpm install` 会把它覆盖掉。
> 更麻烦的是——**官方升级了，你的补丁怎么办？**

---

## 问题的三层

### 第一层：包管理器会覆盖

`pnpm add` / `pnpm install` 重装依赖时，`node_modules` 里你手改的文件全部还原。

**这不算难**：留一份备份，检测到丢失就复制回去。

### 第二层：恢复脚本会把旧版本盖到新版本上

备份是 0.9.7 的，官方升到 0.10.0 了。恢复脚本一跑，
**旧补丁文件覆盖新官方文件** → 半旧半新的混合安装 → 插件起不来。

这类事故比第一层严重得多，而且**很难第一时间发现**：
服务可能还活着，只是某些功能莫名其妙不对。

### 第三层：定时任务在你写到一半时动手

最难查的一种。我的真实经历：

> 升级 0.10.0 时铺完 6 个文件，逐个核对全部正确。几分钟后重启核验，
> 发现 `bridge.js` 变成 1322 行（官方 1440）、`outbound.js` 498 行（官方 666）。
>
> 日志铁证：`[12:28:02] 检测到需要恢复: lib/outbound.js (改动丢失)`
>
> **一个每 30 分钟跑一次的恢复任务，把我刚铺好的文件全盖回了旧版。**

**教训：「改完文件」不等于「改成了」。**
核验必须在**所有写入都结束之后**做，中途核验会被后续覆盖骗过。

---

## 解法

### 一、区分两类文件

| 类型 | 例子 | 恢复方式 |
| --- | --- | --- |
| **全量重写** | 我几乎重写了整个模块 | 整文件从备份复制（MD5 比对确认） |
| **增量补丁** | 在官方文件里插入若干块 | **必须用补丁脚本重新打**，不能整文件覆盖 |

分不清这两类，就会出现「第二层」事故。

### 二、补丁脚本：锚点 + 代码标记

核心思路是「在官方原文里找到确定的位置，替换成加了补丁的版本」，而不是覆盖整个文件。

```python
def patch(rel, name, anchor, replacement, mark):
    """在 rel 文件里把 anchor 替换成 replacement。mark 用于幂等检测。"""
    text = read(rel)
    if mark in text:                      # 已打过 → 跳过
        return
    if text.count(anchor) != 1:           # 锚点必须唯一
        errors.append("%s :: %s —— 锚点不唯一或找不到" % (rel, name))
        return
    write(rel, text.replace(anchor, replacement, 1))
    if mark not in read(rel):             # 写后立刻回读校验
        errors.append("%s :: %s —— 写入后校验失败" % (rel, name))
```

三个关键约束：

| 约束 | 为什么 |
| --- | --- |
| **锚点找不到就报错退出**，不猜着改 | 官方升级后文本必然变化，这时应该人工重新确认，而不是让脚本猜 |
| **写后立刻回读校验** | 「写入成功」≠「内容对」 |
| **可重复运行**（幂等） | 跑十次和跑一次结果一样，才能放进自动化流程 |

### 三、mark 必须是代码，不能是散文 ⚠️

这是我自己踩的坑，很隐蔽：

> 幂等判断的 mark 我一开始写成 `"打字状态通道。"`（一句中文短语）。
> 结果**同一段注释里也有这句话**，于是脚本报「已存在，跳过」，
> 而代码分支根本没插进去 —— **静默漏掉一个关键补丁**，
> 会导致整个打字感知功能失效，且没有任何报错。

**正确做法**：mark 取代码行为的精确文本，例如

```python
"if (subType === 'input_status') {"
```

**散文 mark 会被自己写的注释命中。** 这条几乎每个人第一次写补丁脚本都会犯。

### 四、版本守门

备份目录里放一个 `VERSION` 文件。恢复前比对安装版本：

```python
cur, recorded = version_mismatch()
if recorded and cur and cur != recorded:
    log("⚠ 版本不一致，已中止恢复：安装=%s 备份=%s" % (cur, recorded))
    return          # 只告警，不写入
```

这样官方升级后，恢复脚本会**主动停下**，而不是把旧补丁盖上去。

### 五、恢复任务必须能在升级期间关掉

```bash
schtasks /change /tn "<RestoreTask>" /disable    # 升级前
# ... 升级、打补丁、同步备份、更新 VERSION ...
schtasks /change /tn "<RestoreTask>" /enable     # 升级后
```

## 工作流

```
官方发新版本
    │
    ├─ 1. 关掉恢复定时任务
    ├─ 2. npm pack 下载新版本到临时目录（不直接装）
    ├─ 3. 逐文件 diff：官方改了什么、我改了什么
    ├─ 4. 判断每个冲突：用官方的？保留我的？合并？
    ├─ 5. 铺官方原版文件（保留私有文件，如 presets/）
    ├─ 6. 跑补丁脚本重建全部补丁
    ├─ 7. 语法检查 + 单元测试 + 完整性校验
    ├─ 8. 破坏测试：还原成官方原版，确认脚本能重建
    ├─ 9. 同步备份 + 更新 VERSION
    └─ 10. 重新启用定时任务
```

**第 8 步最重要**，也最容易被跳过：
把文件全部还原成官方原版，再用脚本重建一遍，确认能成功。
不做这步，你永远不知道脚本是不是已经悄悄失效了。

## 适用性

这套方案不限于某一个插件，任何「需要长期维护本地补丁」的场景都能用：

- 上游是 npm 包 / pip 包，且你会被包管理器覆盖
- 上游仍在活跃更新，你需要跟上版本
- 你的改动是「插入式」的，不是整体重写

如果是整体重写（fork），直接维护 fork 更省事。

## 一条元教训

**「能变成检查的，就不要依赖记忆。」**

我一开始靠「记得升级前关掉恢复任务」来避免事故，结果还是忘了——
因为那次是在容器里跑长任务，中途注意力被别的事情打断。

后来改成：恢复脚本自己检查版本号，不一致就停。
**把纪律变成代码，比写十条注意事项有用。**

同样的思路也适用于测试：与其写「注意 flush 里不要删打字历史」，
不如写一条断言 `flush() 里禁止出现 typingStates.delete`。
