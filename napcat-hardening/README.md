# 让 NapCat 长期在线、不触发风控

> QQ 机器人最常见的两个「莫名其妙挂了」：**登录态失效被踢**、**WSL 虚拟机自己关了**。
> 这份文档把两年的踩坑整理成可复用的运维方案。

---

## 一、先说最严重的一次：因为重试太积极被封号 5 天

### 症状

服务挂了两天没人管，事后查日志发现：

```
10-25 ~ 10-26  每约 2 分钟重登一次
累计约 1800 次失败登录
→ [KickedOffLine]
→ 掉线 5 天
```

### 根因

```ini
Restart=always          # 服务崩溃就无限重启
```

配了 `-q`（免扫码）时，重启后会**立刻尝试复用登录态**。
登录态失效时这就是个死循环：崩溃 → 重启 → 登录失败 → 崩溃 → ...

**每 2 分钟一次，五天 1800 次失败登录**，这在腾讯眼里就是暴力破解。

### 修法

```ini
Restart=on-failure
RestartSec=60
StartLimitBurst=3              # 10 分钟内最多 3 次
StartLimitIntervalSec=600
```

把「无限重试」改成「最多试 3 次就停」。

**效果**：改完之后连续在线 **7 天、0 重启、0 掉线**（此前最好记录 23 小时）。

### 关键认知

> **重试不是保护，是攻击。**
> 登录失败时最该做的是**停下来**，而不是更努力地试。

## 二、但 systemd 只防住了第一层

这是 2026-11-08 的重大失误。

### 症状

03:35 登录态失效。但：

```
服务状态:  active
NRestarts: 0
进程:      活着
```

systemd 完全没察觉。可 NapCat **进程内部**自己有个登录重试循环，
每 2 分钟试一次，空转到 09:46，**累计 184 次失败**才被人工叫停。

### 两层循环

| 层 | 机制 | systemd 能看到吗 |
| --- | --- | --- |
| 服务层 | 进程崩溃 → `Restart=` | ✅ 能 |
| **进程层** | 进程活着，内部重试登录 | ❌ **看不到** |

`Restart=on-failure` 只解决第一层。

### 解法：自己数失败次数

```bash
LN=$(grep -an 'OneBot11 适配器初始化完成' service.log | tail -1 | cut -d: -f1)
tail -n +$LN service.log | grep -ac 'Login Error'
```

**关键细节**：

| 要点 | 为什么 |
| --- | --- |
| 只数「本次启动后」 | 全天累计会导致服务一启动就被判异常，永远恢复不了 |
| 用**行号切分**，不解析时间戳 | 见下面的 BUG-3 |
| 加启动宽限期 | `GRACE_SEC = 120`，刚启动别动它（否则还在正常登录就被判失败） |

## 三、三个差点把系统搞坏的 BUG

### BUG-1：失败数用了「全天累计」

服务一启动就继承昨天的失败数 → 立刻判定异常 → 反复重启 → 永远起不来。

**修法**：只统计本次服务启动后的。

### BUG-2：缺启动宽限期

服务刚起 10 秒，登录还没完成，`Login Error` 当然有。
监控一看「有失败」就动它 → 打断正常登录。

**修法**：`GRACE_SEC = 120`。

### BUG-3：用 `awk` 比较时间戳 → 统计出 725 次假失败

```bash
# ❌ 错的写法
awk -v t="$(systemctl show -p ActiveEnterTimestamp --value napcat)" \
    '$0 >= t' service.log | grep -c 'Login Error'
```

因为 `mktime()` 对 `"Sun 2026-11-08 10:32:05 CST"` 这种格式**返回 -1**。
于是「所有行都 >= -1」→ 全部命中 → 报 725 次失败，**真实值是 0**。

**修法**：按行号切分，完全不碰时间解析（就是上面那段 `grep -an ... | cut -d: -f1`）。

> 这个 bug 的危险在于它**看起来能跑**，只是数字完全错误。
> 而且错误方向是「误报故障」→ 会触发不必要的停服。

## 四、分级处置：先自愈，后升级

一定要「重启试试」，不要「一失败就停服」。

```
第 1 级  失败达阈值(10)      → systemctl restart napcat
第 2 级  重启后仍失败        → 再重启，最多 3 次
第 3 级  重启次数用尽        → systemctl stop napcat（止血，等人工扫码）
```

### 为什么「一失败就停服」是错的

我最初就是「达阈值直接停服」，以为稳。结果用户问：

> 「为什么没扫码也登上去了？」

查日志发现铁证：

```
11-08 10:25:43  接收 <- 临时消息 (2909288299)    ← 真实消息收发，登录成功
```

真相：重启 Worker 杀掉了带 `-q` 的旧进程，新 Worker **复用本地登录态直接上线，根本不需要扫码**。

> **`ErrCode 3` 不等于「必须扫码」。重启 Worker 常常就能自愈。**

所以「一失败就停服」不但没用，还**切断了唯一的自愈路径**。

## 五、WSL2 虚拟机自己关了（最容易被误判）

### 症状

NapCat 反复挂。`journalctl` 里全是 `Stopping`，但**没有崩溃记录**。

### 根因

**WSL2 在最后一个 `wsl.exe` 客户端退出后约 8 秒，自动关闭整个虚拟机。**

systemd 随之**优雅停掉所有服务**（`Stopping`，不是崩溃）→ 看起来像 NapCat 不稳定。

### 修法：常驻一个 keepalive 客户端

```powershell
# 启动文件夹放一个 VBS，后台常驻（免管理员、无窗口）
wsl -d Ubuntu -- bash -c "while true; do sleep 3600; done"
```

### 怎么判断是不是这个原因

| 现象 | 含义 |
| --- | --- |
| `journalctl` 里 `Stopping` 是 orderly 优雅停止 | VM 被关机，不是崩溃 |
| 日志出现 `-- Boot --` 分隔线 | VM 重启过 |

## 六、账号级风控：脚本能做的和不能做的

### 能做的（按有效性排序）

| 优先级 | 措施 | 治什么 |
| --- | --- | --- |
| ① | 禁掉 `-q` 重试循环 | **最关键**，直接避免登录风暴 |
| ② | `o3HookMode=0` | 关签名 hook，减少可识别痕迹 |
| ③ | 出站内容去重 | 不发重复内容，不像机器人 |
| ④ | 按字数抖动延迟 | 打字速度像人 |
| ⑤ | webui `loginRate=3` | 登录请求限速 |

### 做不到的（必须承认）

**降低账号级风控频率，脚本层面无解。**

我的实测数据：某次会话持续 3 天 16 小时，期间**只有 13 条私聊消息**：

```
10-25: 56 条    10-31:  3 条    11-01: 29 条
11-03: 15 条    11-06: 17 条    11-08:  3 条
11-11: 11 条
```

**职业画像很清晰：「长期沉默 + 偶尔爆发」。**

这类账号在风控系统眼里风险高于「每天活跃几十条」的正常用户。
而企微/QQ 的风控提示**不会进 NapCat 日志**，只有手机端能看到。

> **唯一有效的手段是：手机上长期同时登录这个账号。**
> 让它的活跃度看起来像真人。

### 掉线后的正确做法

| 时段 | 该做什么 |
| --- | --- |
| 工作日（不在电脑旁） | 停服止血，写日志，**不要反复重试**。留到周末 |
| 周末（能扫码） | 重启服务，出新码，扫码 |

**不要在失败后连续重试** —— 那正是上次招来风控的原因。

## 七、一个健康检查清单

```bash
# 1. 端口在听吗
ss -tn | grep 3002

# 2. 有客户端连上吗（关键：光在听不代表连上了）
ss -tn | grep 3002 | grep ESTAB

# 3. 本次启动后失败几次
LN=$(grep -an 'OneBot11 适配器初始化完成' service.log | tail -1 | cut -d: -f1)
tail -n +$LN service.log | grep -ac 'Login Error'

# 4. 有没有被踢
grep -c 'KickedOffLine' service.log

# 5. 服务状态与重启次数
systemctl status napcat --no-pager
```

**别只看端口和 `KickedOffLine`** —— 凭证过期（`ErrCode 3`）**不会留 `KickedOffLine` 痕迹**，
整夜静默空转，看起来一切正常。

## 总结：五条硬教训

1. **重试不是保护，是攻击。** 登录失败时最该做的是停下来。
2. **「不要重启」≠「不要停止」。** 看到失败持续刷就先停服止血再报告。
3. **健康检查必须看失败次数**，不能只看端口。凭证失效不留痕迹。
4. **`ErrCode 3` 不等于必须扫码。** 重启 Worker 常常自愈，别切断这条路。
5. **能变成检查的，就不要依赖记忆。** 把「注意 X」写成断言，比写十条注意事项有用。
